Por onde o aplicativo começa e como o menu leva a cada tela.

lib/main.dart

Ponto de entrada

Todo app começa em main(), que entrega o widget raiz para o runApp().

main()→runApp()→MeuApp→MaterialApp→HomeScreen
  • main(): ponto de partida de qualquer programa Dart. Aqui chama runApp(const MeuApp()), que transforma MeuApp na raiz visual da interface.
  • MeuApp: um StatelessWidget cujo único trabalho é construir o MaterialApp.
  • MaterialApp: configura o app inteiro. title é o nome do app, theme gera a paleta a partir do índigo usando Material 3, e home define a primeira tela.
Ligação com o tópico 10

Sem home (e sem alternativas como routes ou onGenerateRoute), o app não sabe o que mostrar. O tópico 10 tem uma demonstração disso.

lib/screens/home_screen.dart

Tela de menu

Uma lista de tópicos em que cada item, ao ser tocado, empilha uma nova tela com o Navigator.

O código tem três peças principais:

  • _Topico: classe privada que serve de molde de dados (título, subtítulo, ícone e uma função builder que cria a tela). Ela não é um widget, apenas organiza as informações de cada item.
  • ListView.separated: constrói os itens com itemBuilder e coloca um Divider entre eles com separatorBuilder. É uma variação do ListView.builder que acrescenta separadores.
  • ListTile + onTap: a linha Navigator.of(context).push(MaterialPageRoute(builder: topico.builder)) é a que troca de tela, empilhando a nova sobre a atual. O botão de voltar desempilha.

models/pessoa.dart + screens/polimorfismo_screen.dart

1. Polimorfismo

Uma variável do tipo Pessoa pode guardar um Estudante, e a versão do método executada é sempre a do tipo real do objeto.

  • Estudante extends Pessoa herda o campo nome e o método saudacao().
  • Com @override, ele sobrescreve saudacao(), icone e cor.
  • Estudante(String nome, this.curso) : super(nome) repassa o nome para o construtor de Pessoa.

O que a tela mostra

A lista é declarada como List<Pessoa>, mas mistura objetos Pessoa e Estudante. O mesmo código pessoa.saudacao() produz textos, ícones e cores diferentes conforme o tipo real.

O subtítulo usa pessoa.runtimeType, que revela esse tipo real.

Inconsistência no material

A seção de modelos tem o título "regras de negócio, sem Flutter", mas pessoa.dart importa package:flutter/material.dart para usar IconData e Color. O próprio texto admite a exceção. models/conta.dart + screens/encapsulamento_screen.dart

2. Encapsulamento

Os dados ficam privados e só mudam através de métodos que aplicam as regras.

  • O prefixo _ torna _numero e _saldo privados.
  • Leitura: getSaldo() e o getter numero.
  • Escrita: depositar() e sacar(), que validam se o valor é positivo e, no saque, se há saldo suficiente. Se a regra falhar, o método lança um erro (ArgumentError ou StateError).

Ver código da tela
Pontos de atenção
  • Privacidade em Dart é por arquivo. O material diz que os campos são acessíveis "só de fora da classe" pelos métodos. Em Dart, o _ torna o membro privado à biblioteca (o arquivo), e não à classe. Qualquer código dentro de conta.dart enxerga _saldo. A conclusão do material continua certa: nenhum outro arquivo consegue mexer no saldo diretamente.
  • Mensagens com prefixo. Como a tela usa e.toString(), o usuário vê "Invalid argument(s): O valor do depósito deve ser positivo." e "Bad state: Saldo insuficiente.". Para mostrar só o texto, seria preciso ler e.message.
  • Falta o dispose(). Todo TextEditingController criado no State deveria ser liberado com _valorController.dispose() dentro de um método dispose(). Não quebra o exemplo, mas é uma boa prática que costuma ser cobrada.
  • Estilo. getSaldo() é um hábito vindo do Java. O jeito idiomático em Dart é um getter, como o próprio código faz com numero: double get saldo => _saldo;.
models/produto.dart + screens/parametros_nomeados_screen.dart

3. Parâmetros nomeados

Parâmetros entre chaves { } são passados pelo nome, e não pela posição.

Produto(nome: 'Celular', preco: 1200)certo
Produto('Celular', 1200)erro de compilação

Como os campos são anuláveis (String? e double?), os dois parâmetros são opcionais. Por isso Produto(nome: 'Capa Protetora') é válido, e a tela mostra um traço no lugar do preço quando ele é null.

arrow_back3. Parâmetros Nomeados
Tratando o null na tela

produto.nome ?? '(sem nome)' usa o operador ??: se o valor da esquerda for null, usa o da direita.

produto.preco! usa o ! para afirmar que o valor não é nulo. Isso é seguro aqui porque vem logo depois do teste produto.preco != null.

Ver código da tela
Complemento que costuma cair
  • {required this.nome}: parâmetro nomeado obrigatório. Sem ele, o campo precisaria ser anulável ou ter valor padrão.
  • {this.preco = 0}: nomeado com valor padrão.
  • [this.preco]: posicional opcional, usando colchetes.

5. Regras de construtores

Três regras numa classe só: this. nos parâmetros, redirecionamento com this(...) e mistura de posicional com nomeado.

  • this.largura no construtor principal: atalho que atribui o valor direto ao campo.
  • Retangulo.quadrado(lado) : this(lado, lado): redireciona para o construtor principal, passando o mesmo valor duas vezes.
  • Retangulo.comEscala(base, {escala = 1.0}): base é posicional e escala é nomeado opcional com valor padrão.

Pontos de atenção
  • Quebra de linha dentro da string. No PDF, a linha 'Dimensões: $retangulo | Área: ...' aparece quebrada no meio do texto entre aspas. Isso parece ser só a formatação do documento, mas se for digitado assim dá erro de compilação, pois uma string com aspas simples não pode atravessar linhas. Mantenha tudo numa linha só (como no código desta página) ou use aspas triplas.

Ordem completa (com herança)

Quando a classe estende outra, a sequência é: parâmetros this., lista de inicializadores, construtor da superclasse (super(...)) e, por último, o corpo. Na lista de inicializadores ainda não se pode usar this para ler outros campos, porque o objeto não terminou de ser montado.

12. TextField e labelText

O labelText fica dentro do campo quando ele está vazio e sem foco, e sobe para a borda quando o campo recebe foco ou tem texto.

Os três estados

Opções do mainAxisAlignment

startFilhos juntos no início do eixo; a sobra fica no fim. É o padrão.
endFilhos juntos no fim do eixo; a sobra fica no início.
centerFilhos juntos no meio; a sobra é dividida igualmente entre as duas pontas.
spaceBetweenSobra dividida só entre os filhos. O primeiro encosta no início e o último no fim.
spaceAroundCada filho recebe a mesma margem dos dois lados. Por isso, nas pontas fica metade do espaço que há entre dois filhos.
spaceEvenlyTodos os espaços iguais, inclusive os das pontas.

Opções do crossAxisAlignment

centerCada filho centralizado no eixo cruzado. É o padrão.
startFilhos alinhados no início do eixo cruzado (topo no Row, esquerda no Column).
endFilhos alinhados no fim do eixo cruzado (base no Row, direita no Column).
stretchForça cada filho a ocupar todo o eixo cruzado. É o que o professor usa na tela de encapsulamento para o card, o campo e os botões ocuparem toda a largura.
baselineAlinha os filhos pela linha de base do texto, útil quando há textos de tamanhos diferentes lado a lado. Exige também textBaseline: TextBaseline.alphabetic.

mainAxisSize

maxO Row/Column ocupa todo o espaço disponível no eixo principal. É o padrão.
minOcupa só o necessário para os filhos. Sem sobra de espaço, o mainAxisAlignment deixa de ter efeito visível. Aparece no app nas telas de Scaffold e de contador, junto com o Center.
Pegadinhas que costumam cair
  • O eixo cruzado se ajusta ao maior filho. Um Row tem a altura do filho mais alto, e um Column tem a largura do filho mais largo. Por isso crossAxisAlignment.center num Row centraliza os filhos entre si, sem centralizar o Row na tela. Com stretch, ele passa a ocupar todo o espaço cruzado disponível.
  • baseline sem textBaseline dá erro. E num Column o baseline não faz sentido (linhas de base são horizontais), então o Flutter trata como start.
  • stretch em espaço infinito dá erro. Um Row com stretch dentro de uma lista vertical, por exemplo, tentaria ter altura infinita.
  • Expanded "come" a sobra. Se algum filho estiver dentro de um Expanded ou houver um Spacer, não sobra espaço livre e o mainAxisAlignment deixa de ter efeito. É o que acontece com os dois botões da tela de encapsulamento.
  • start e end dependem da direção. No Row, seguem a direção do texto (em idiomas escritos da direita para a esquerda, start fica à direita). No Column, seguem o verticalDirection, que por padrão vai de cima para baixo.
